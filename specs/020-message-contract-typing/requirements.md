# 020 消息契约类型化

## 背景与目标

理赔申请服务的三条 MQ 链路共用 `ClaimApplicationEventEnvelope`，其中 `payload` 是 `Map<String, Object>`。生产侧用 `Map.of` 拼字段，消费侧用字符串 key 取值并做 `instanceof` 判断，字段名、类型和必填约束都只存在于运行期。新增一个字段时，编译器无法提示生产侧漏写、消费侧拼错 key 或类型不匹配。

本次目标是把消息契约从“通用信封 + Map 载荷”改为“封闭消息类型 + 类型化载荷”：

- 每条消息有唯一的具体类型，载荷字段以 record 组件声明，编译期可校验。
- 消息集合封闭，新增消息类型必须显式扩展契约，不能靠约定。
- 消费侧只做业务校验，不再从 Map 猜字段类型。

本次是纯实现层重构，对外 MQ 契约、HTTP 契约、数据库与 Redis 均不变。

## 业务规则

1. 平台对外共三类消息：材料处理、审核交付、审核签收；每类消息有唯一消息类型与唯一载荷类型。
2. 消息公共字段固定为 `eventId`、`eventType`、`eventVersion`、`claimApplicationNo`、`tenantCode`、`occurredAt`、`traceId`；载荷字段按消息类型定义。
3. 对外 JSON 的字段名、层级、取值语义与 018 交付结果完全一致；Topic、消费组、事件类型字符串、重投次数、死信主题与幂等键均不变。
4. 消息类型集合封闭，只能通过修改密封接口扩展；新增消息类型必须同时补齐生产、消费与测试。
5. 出站消息与入站消息在类型层区分，Outbox 投递端口只接受出站消息，不能传入审核签收等入站专属类型。
6. 消息字段与载荷字段在契约层显式声明，生产侧不得再用 `Map<String, Object>` 拼接载荷。
7. 消费侧不得再用字符串 key 读取载荷；字段缺失或类型不符必须显式失败，不允许静默取到 null 后继续处理。
8. 材料处理消息的 `claimApplicationAttempt` 仍为必填业务字段，缺失时消费失败并进入既有重投与死信流程。
9. 审核交付消息继续只依赖消息公共字段，载荷中的申请尝试次数不参与消费决策。
10. 审核签收消息的校验规则保持不变：`eventType` 必须为 `AUDIT_SIGNED`，`eventId`、`claimApplicationNo`、`tenantCode` 非空白，`caseNos` 为非空字符串数组，案件号去空白后非空、不超过 64 字符、去重后落库；非法消息错误码仍为 `AUDIT_SIGNED_INVALID`。
11. 审核签收消息的未知额外字段继续被容忍；案件号数组中的非字符串元素继续被拒绝。
12. Outbox 存储仍为 JSON 字符串；投递调度按事件类型把存储载荷转换成对应消息类型，未知事件类型、载荷 JSON 非法或字段类型不符仍按投递失败处理，进入既有退避重试与失败标记流程。
13. 消息 `traceId` 仍取自存储载荷，缺失时回退为 `eventId`，与现状一致。
14. 消息消费失败仍原样抛给 binder，由 binder 重投并最终进入死信；业务拒绝日志、系统异常日志与敏感字段脱敏要求不变。

## 正常场景

- 首次签收或重新申请写入 Outbox 事件，投递调度构造材料处理消息，材料消费者直接读取类型化的申请尝试次数并处理。
- 申请进入 `WAIT_AUDIT` 写入审核交付事件，投递调度构造审核交付消息，审核交付消费者直接读取公共字段并交付。
- 审核系统回传 `AUDIT_SIGNED`，消息反序列化为审核签收类型，装配器读取类型化案件号列表，完成校验、去空白与去重后落库。
- 事件字段与载荷字段在序列化后与 018 契约文档逐字段一致，既有外部消费者无需改动。

## 异常场景与边界条件

- 事件类型不在出站事件集合内：投递调度拒绝构造消息，事件按现有规则退避重试或标记失败。
- Outbox 存储载荷不是合法 JSON，或字段类型与契约不符：投递调度按投递失败处理，不发送半成品消息。
- 审核签收消息缺少 `caseNos`、数组为空、案件号空白或超过 64 字符：装配器返回 `AUDIT_SIGNED_INVALID`，消息重投后进入死信。
- 审核签收消息的 `caseNos` 含非字符串元素：消息转换阶段失败，按消费失败进入重投与死信，不写入案件关系。
- 材料处理消息缺少 `claimApplicationAttempt`：消费者显式失败，按既有规则重投与死信。
- 消息顶层或载荷出现契约外字段：继续容忍，不影响已知字段解析。
- 消息 `payload` 为 `null`：审核交付消费者不受影响；材料处理与审核签收按各自必填规则失败。
- 历史 Outbox 行若包含契约外的载荷字段，转换后不再透传到 MQ；契约字段与取值不受影响。

## 本次范围

- `claim-application-service` 的 MQ 消息契约、Outbox 载荷构造与投递转换、三个消费者与审核签收装配器。
- 契约序列化/反序列化测试、既有装配器测试迁移、投递转换测试。
- 架构文档中的跨域契约条目。
- 运行栈三条 Topic 与死信链路回归。

## 非本次范围

- 不修改对外 JSON 字段名、层级与语义，不修改 Topic、消费组、事件类型字符串、重投次数、死信主题与幂等键。
- 不修改 MQ 死信策略、补偿策略与消费幂等实现。
- 不修改 HTTP 接口、错误码、响应结构。
- 不修改网关、租户、案件、AI 模块。
- 不调整领域模型、数据库、Redis 与 Outbox 表结构。
- 不引入消息版本升级机制，不实现多版本消息兼容。
- 不引入新的序列化框架或依赖。

## 验收标准

1. `ClaimApplicationEventEnvelope` 删除且代码无引用（历史 spec 文档除外）；消息生产与消费代码中不再出现 `Map<String, Object>` 载荷与 `payload.get(...)`。
2. 三类消息均有独立消息 record 与载荷 record，顶层接口与出站接口均为密封接口，新增实现必须显式声明。
3. 契约测试序列化三类消息，字段名与 018 契约文档逐字段一致；契约文档中的审核签收样例可反序列化为类型化消息。
4. 审核签收的全部校验规则与错误码与 018 交付结果一致，非字符串案件号仍被拒绝。
5. 材料处理、审核交付、审核签收三条链路在运行栈上的成功、重投与死信行为与 018 一致，Topic 与消费组不变。
6. 全量 Maven 构建与测试通过，既有分层 ArchUnit 规则继续通过。
7. 架构文档不再出现 `ClaimApplicationEventEnvelope`，并说明消息契约的封闭类型结构。

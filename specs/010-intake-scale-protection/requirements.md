# 010 签收扩容保护：判定快照缓存、网关租户限流与 Redis 降级

## 项目背景与目标

签收入口当前有三处保护缺口：

1. 判重只回答"是否已签收"：`RedisClaimApplicationExistenceQuery` 缓存的只是布尔存在性，真正的处置判断（复用还是重新申请）仍在事务里回源读聚合。重复请求越多，回源读库越多。
2. 入口没有按租户限流：每实例默认 5 条数据库连接，一个租户重推就能把连接池占满，连带影响其他租户与 MQ 消费。
3. Redis 故障时行为不可预期：签收锁降级为无锁、存在性逐请求回源、发号退化为"取当天最大号 + 1"，并发下靠唯一键冲突重试收敛，重试耗尽直接失败。

本 Spec 的目标：

- 把"已过受理"的单调事实写进缓存，重复请求不再读库，同时保持"受理失败可重新提交"的语义。
- 网关按租户限流，给出可计算的入口上界。
- Redis 故障时只降速、不换方案：保留 Redis 计数发号，降级路径串行化、可观测，Redis 恢复后自动追平。

## 业务规则

### 签收判定缓存

1. 缓存键为 `sha256(租户编码:外部申请号)`，与现有存在性缓存保持同一键空间语义。
2. 缓存值只包含平台申请编号与状态，且仅当状态属于 `ACCEPTED`、`UNDERWRITING`、`WAIT_AUDIT` 时写入。
3. 命中缓存时直接按重复请求返回 `REUSED` 与平台申请编号，不读取聚合、不调用外部系统。
4. `PENDING_ACCEPT` 与 `ACCEPT_FAILED` 不作为可直接复用的判定依据，必须回源数据库确认状态后再决定复用或重新申请。
5. 缓存不需要任何失效动作：安全状态集合在状态机中单调不可逆，进入后不会再回到 `ACCEPT_FAILED`。快照 TTL 1 小时，读时回填。
6. 不存在的外部申请号缓存空标记，TTL 1 分钟，防穿透；该申请创建成功后覆盖为存在标记，避免空标记把刚创建的申请误判为不存在。
7. 缓存不可用时不得改变业务结论：回源数据库后按原规则判定。

### 网关限流

8. 限流按「路由兜底 + 接口级租户配额」两层执行：路由兜底统计该路由下的全部请求，接口级配额按租户编码（`X-Tenant-Code`）维度只统计命中该接口的请求。
9. 同一路由下不同接口的租户配额互不影响：签收接口超限时，同租户对承保回调等其他接口的请求不受牵连。
10. 单节点阈值由配置给出；未在接口级配置的租户只受路由兜底阈值约束。租户的全局上界等于单节点阈值乘以网关节点数，文档必须写明该口径。
11. 超过任一阈值返回 HTTP 429 与错误码 `CLAIM_APPLICATION_RATE_LIMITED`，请求不进入业务服务。
12. 缺少租户头的请求由现有过滤器直接 400 拒绝，不进入限流统计。
13. 限流规则随应用启动从配置加载，控制台只用于观测，不作为规则的维护来源；控制台上临时改动的规则在网关重启后失效。

### Redis 降级

14. 发号继续以 Redis 当日计数器为准，编号格式与长度不变。
15. Redis 调用失败时必须在本节点串行生成编号，禁止并发读取同一天最大号。
16. 唯一键冲突继续由数据库唯一约束与用例重试兜底，重试次数上限由 3 次提高到 5 次。
17. Redis 连续失败达到阈值后熔断 10 秒，熔断期间锁、缓存、发号直接走降级路径，不再逐请求等待 Redis 超时。
18. 熔断到期后允许探测，Redis 恢复正常路径使用，无需人工介入。
19. 熔断关闭后的首次发号必须先把 Redis 计数器抬升到数据库已落库的最大尾号，避免回退撞号。
20. 降级期间本节点签收并发受信号量限制（默认 10），超出直接返回 `CLAIM_APPLICATION_INTAKE_SYSTEM_ERROR`，不排队。
21. 降级日志每条之间至少间隔 10 秒，包含降级原因与当前并发数，不输出报文与个人信息。

## 正常场景

1. 首次签收：缓存无记录 → 回源确认为新申请 → 创建成功，状态 `PENDING_ACCEPT`；不写可复用快照，创建后把存在标记写入缓存。
2. 重复签收且已缓存：命中快照 → 直接返回 `REUSED` 与平台申请编号 → 只写交互轨迹。
3. 首次重复且未缓存：回源读到状态 `WAIT_AUDIT` → 返回 `REUSED` → 回填快照 → 后续重复走缓存。
4. 受理失败后重新提交：不按缓存直接复用 → 回源读到 `ACCEPT_FAILED` → 重新申请 → 返回 `REAPPLIED`。
5. 限流阈值内：请求正常进入业务服务，其他租户、同一租户的其他接口互不影响。
6. Redis 恢复：熔断关闭 → 首次发号抬升计数器 → 后续编号连续唯一。

## 异常场景

1. Redis 不可用：锁、缓存、发号全部走降级，签收仍成功且编号唯一，降级日志按 10 秒间隔输出。
2. 熔断期间并发超过降级上限：直接返回 `CLAIM_APPLICATION_INTAKE_SYSTEM_ERROR`，请求不进入锁与事务。
3. 降级期间多节点同时发号：唯一键冲突由用例重试收敛，最多 5 次，耗尽后按系统异常返回。
4. 超过接口级租户配额或路由兜底阈值：网关返回 429 与 `CLAIM_APPLICATION_RATE_LIMITED`，业务服务不产生签收日志与轨迹。
5. 缓存与库不一致：以库为准；缓存只承载安全状态，不一致最多多读一次库，不会改变处置结论。

## 边界条件

1. 缺少租户头：网关现有过滤器返回 400，不进入限流桶。
2. 安全状态集合之外的申请：永不作为可直接复用的判定依据。
3. 空标记过期后，下一次请求回源数据库并按结果重新回填。
4. 熔断到期后的第一个请求承担探测职责，探测失败立即重新打开。
5. 网关多节点时，租户全局上限按"单节点阈值 × 节点数"计算，阈值配置不得写成期望的全局值。
6. 发号格式保持 `A` + `yyyyMMdd` + 8 位序列，不因降级改变。
7. 未在接口级配置的路径只受路由兜底约束；未在接口级配置的租户同样只受路由兜底约束。
8. 接口路径匹配支持精确、前缀、正则三种策略，默认精确。
9. 控制台不可用不影响限流：心跳上报失败既不改变规则，也不阻断请求。

## 本次范围

- 存在性缓存改为"平台申请编号 + 安全状态"快照，并新增进程内 L1 缓存。
- 网关引入 Sentinel 做「路由兜底 + 接口级租户配额」两层限流与统一 429 响应，签收接口与承保回调不再共用租户配额。
- 本地部署 Sentinel 控制台，用于观测实时 QPS、拒绝数与机器状态。
- Redis 可用性熔断、发号降级串行化、降级并发闸门与降级日志。
- 契约、架构、联调文档同步。

## 非本次范围

- 号段发号与序列表（并发量不支持该复杂度，已裁定不引入）。
- Sentinel 集群流控与 token server。
- 基于 Redis 的全局分布式限流。
- 编号连续性与对账能力。
- 多级缓存一致性协议（失效广播、版本号等）。
- 通过控制台维护或持久化限流规则（Nacos/文件数据源）；控制台只做观测。

## 验收标准

1. 重复签收命中快照时返回 `REUSED`，且不产生聚合查询；未命中的首次重复会在回源后回填快照。
2. `ACCEPT_FAILED` 的申请用同一外部申请号重新提交返回 `REAPPLIED`，缓存中不存在该申请的可复用快照（`A…|状态`）。
3. 停掉 Redis 后连续提交 10 个申请全部成功，编号唯一，降级日志相邻两条间隔不小于 10 秒。
4. Redis 恢复后继续提交，编号不与已落库编号冲突，Redis 计数器尾号不小于数据库最大尾号。
5. 签收接口超过租户配额时网关返回 429 与 `CLAIM_APPLICATION_RATE_LIMITED`，同租户请求承保回调接口不受影响；未超限租户请求正常。
6. `mvn -B clean package` 全反应堆通过；运行日志中无证件号、报文原文与文件地址。
7. 网关启动后 Sentinel 控制台能看到 `claim-gateway` 机器与签收接口的实时 QPS；控制台上新增的规则在网关重启后不再生效。

# 025 理赔申请全链路编排、问题件交互与审核完成

## 背景与目标

024 已把 `ClaimApplication` 收敛为唯一聚合根，签收、材料处理、承保分流、问题件下发/关闭与审核签收均已落到聚合状态机。当前链路仍有四个未收口的问题：

1. `WAIT_AUDIT` 是事实上的最后一站：审核签收只追加 `ClaimCaseRelation`，不推进申请状态，申请永远不会到达终态。
2. 审核签收不校验消息租户与申请租户是否一致，也不校验申请状态；案件关联写入与申请生命周期脱节。
3. 问题件只有一个 `auditor` 字段，关闭时覆盖下发人，问题件历史无法区分“谁下发、谁关闭”。
4. `WAIT_AUDIT` 没有滞留补偿；审核交付或审核签收消息丢失后，申请只能人工排查。

目标：

- 补齐理赔申请从签收到审核完成的全生命周期状态机，新增终态 `COMPLETED`。
- 把审核签收定义为“审核系统完成签收并返回全部案件号”的完成事实，在同一个事务内完成案件关联追加与申请终态迁移。
- 明确问题件在全生命周期各状态下的可执行操作，并保留问题件下发人与关闭人的完整轨迹。
- 为 `WAIT_AUDIT` 增加滞留补偿，覆盖审核交付丢失与审核签收消息丢失两种场景。
- 同步存储、读模型、集成契约与验证文档，使完整链路可运行、可重复、可诊断。

本 Spec 中的“审核完成”指审核系统完成签收并回传全部案件号，理赔申请在平台的受理职责结束；审核结论、案件阶段与案件后续生命周期仍由审核系统和案件服务承载。

## 业务规则

### 生命周期状态机

1. 理赔申请状态新增终态 `COMPLETED`，表示审核系统已完成签收并返回案件号，理赔申请在平台内的生命周期结束。
2. 允许的状态迁移如下，除此之外一律拒绝：
   - `PENDING_ACCEPT → ACCEPTED`（全部材料处理成功）
   - `PENDING_ACCEPT → ACCEPT_FAILED`（任一材料处理失败）
   - `ACCEPT_FAILED → PENDING_ACCEPT`（重新申请）
   - `ACCEPTED → WAIT_AUDIT`（存在有效保单）
   - `ACCEPTED → UNDERWRITING`（不存在有效保单）
   - `UNDERWRITING → WAIT_AUDIT`（承保完成）
   - `WAIT_AUDIT → ISSUE`（下发问题件）
   - `ISSUE → WAIT_AUDIT`（审核系统关闭问题件）
   - `ISSUE → PENDING_ACCEPT`（租户补材，同时关闭未关闭问题件）
   - `WAIT_AUDIT → COMPLETED`（审核签收完成）
3. `COMPLETED` 是终态：不得再迁移到任何状态；重新申请、租户补材、下发问题件、关闭未关闭问题件均不得修改已完成的申请。
4. 进入 `COMPLETED` 时必须同时记录完成时间；其他状态完成时间为空。
5. `COMPLETED` 申请属于签收可复用状态：同一租户、同一外部申请编号的重复提交直接返回既有 `claimApplicationNo` 与 `REUSED`，不读取聚合、不触发重新申请或补材。

### 审核签收与完成

6. 审核签收消息必须携带 `eventId`、`claimApplicationNo`、`tenantCode` 与非空 `caseNos`；消息中的 `tenantCode` 必须与申请所属租户一致，不一致按消息非法拒绝，不写入任何数据。
7. 审核签收只在申请处于 `WAIT_AUDIT` 或 `COMPLETED` 时被接受：
   - `WAIT_AUDIT`：追加本次缺失的案件关联，并把申请迁移到 `COMPLETED`，记录完成时间。
   - `COMPLETED`：只追加本次缺失的案件关联，不改变状态与完成时间。
   - 其他状态：按状态不合法拒绝，不写入消费登记、案件关联、交互轨迹或状态变更。
8. 审核签收必须在同一个事务内完成消费登记、案件关联追加、申请终态迁移、完成时间写入与 `AUDIT_SIGNED` 交互轨迹写入；任一失败整体回滚。
9. 同一 `eventId` 重复投递按 `SKIPPED` 处理，不重复写库。
10. 同一申请的不同 `eventId` 可以分批返回案件号：已存在的案件号不重复插入，只补插缺失案件号；已完成申请追加新案件号时保持 `COMPLETED`。
11. 审核签收进入 `COMPLETED` 前必须不存在未关闭问题件；若数据异常导致存在未关闭问题件，按状态不合法拒绝，不允许带着问题件完成。
12. 审核签收失败（租户不一致、状态不合法、版本冲突、数据库异常）时不写任何业务数据；消息按既有重投与死信机制处理，由人工排查后重放。

### 问题件交互

13. 下发问题件只允许申请处于 `WAIT_AUDIT` 且当前没有未关闭问题件；下发后申请进入 `ISSUE`。
14. 审核系统关闭未关闭问题件只允许申请处于 `ISSUE`；关闭后申请回到 `WAIT_AUDIT`。已关闭问题件再次关闭按幂等返回 `closed=false`，不校验申请状态。
15. 租户补材只允许申请处于 `ISSUE` 且存在未关闭问题件；补材关闭未关闭问题件后状态回到 `PENDING_ACCEPT`，关闭人记为 `TENANT_SUPPLEMENT`。
16. `COMPLETED` 申请不得下发新问题件；对 `COMPLETED` 申请携带平台编号提交按重复请求复用，不触发补材。
17. 问题件下发人与关闭人分别记录：下发时记录下发人，关闭时记录关闭人；关闭不得覆盖下发人。
18. 租户补材关闭问题件时，关闭人为平台常量 `TENANT_SUPPLEMENT`，下发人保持原值。
19. 历史问题件全部保留；无法从历史数据恢复关闭人时，关闭人允许为空，但下发人必须保留。
20. 审核系统问题件请求字段 `auditor` 保持不变：下发请求中的 `auditor` 映射为下发人，关闭请求中的 `auditor` 映射为关闭人；问题件查询响应使用 `raisedBy`、`closedBy` 分别返回两种角色。

### 后续链路与补偿

21. 完整异步链路为：签收落库 → 材料处理 → 受理成功 → 承保分流/承保完成 → 审核交付 → 审核签收 → `COMPLETED`；每个阶段只允许在当前状态符合预期时推进。
22. `WAIT_AUDIT` 滞留超过阈值时执行审核签收补偿：
    - 审核系统返回已签收及案件号：按审核签收完成规则推进到 `COMPLETED`。
    - 审核系统返回处理中：保持 `WAIT_AUDIT`，不写状态变更。
    - 审核系统返回未找到：以新的投递事件重新交付审核系统，申请保持 `WAIT_AUDIT`。
    - 审核系统查询失败：记录错误日志，等待下一轮补偿，不改变状态。
23. 审核签收补偿与正常 MQ 消息并发时，只有一方可以完成状态迁移；另一方按已完成申请幂等补齐案件关联。
24. `COMPLETED` 不参与任何滞留补偿；迟到消息、重复消息只记录日志或幂等追加案件关联，不改变终态。
25. 材料处理、承保分流、承保回调、审核交付与问题件读写的既有幂等规则保持不变；本 Spec 只补齐审核签收完成与 `WAIT_AUDIT` 补偿。

### 存储与查询

26. `t_claim_application` 增加可空完成时间列，`COMPLETED` 时非空，其他状态为空；既有状态索引继续支撑滞留扫描。
27. `t_claim_application_issue` 拆分下发人与关闭人两列：原审核人列改为下发人，新增可空关闭人列；未关闭问题件关闭人为空。
28. `t_claim_case_relation` 增加按租户与案件号查询的索引，支撑按案件号反查申请的既有接口。
29. 详情查询摘要增加完成时间；问题件查询返回下发人与关闭人；空值按 `null` 返回，不改变既有响应包裹结构。
30. 查询仍只走读模型，不加载聚合、不写交互轨迹；跨租户与不存在继续返回 `CLAIM_APPLICATION_QUERY_NOT_FOUND`。

### 错误码与契约

31. 审核签收租户不一致新增异步错误码 `AUDIT_SIGNED_TENANT_MISMATCH`；审核签收状态不允许完成新增异步错误码 `AUDIT_SIGNED_STATUS_INVALID`。两者均按消息处理失败重投，耗尽后进入既有死信主题。
32. 审核签收 Topic、消费者组、消息信封与 `payload.caseNos` 结构不变；问题件 HTTP 路径与请求字段不变。
33. 问题件查询响应新增 `raisedBy`、`closedBy`，移除原单一 `auditor` 字段；该接口由 024 新增，当前无外部消费者，允许本次调整。
34. 申请详情摘要新增 `completedAt` 字段；既有字段与响应包裹结构保持不变。

## 正常场景

- 有保单链路：签收 → 材料处理成功 → `ACCEPTED` → 存在有效保单 → `WAIT_AUDIT` → 审核交付 → 审核签收返回两个案件号 → 同一事务写入两条案件关联、迁移 `COMPLETED`、记录完成时间与轨迹。
- 无保单链路：签收 → 材料处理成功 → `ACCEPTED` → 无有效保单 → `UNDERWRITING` → 承保完成回调 → `WAIT_AUDIT` → 审核交付 → 审核签收 → `COMPLETED`。
- 问题件链路：`WAIT_AUDIT` 下发问题件 → `ISSUE` → 审核系统关闭问题件 → `WAIT_AUDIT` → 审核签收 → `COMPLETED`。
- 补材链路：`ISSUE` 租户补材 → 关闭问题件（关闭人 `TENANT_SUPPLEMENT`）→ `PENDING_ACCEPT` → 材料处理 → 承保分流 → 审核交付 → 审核签收 → `COMPLETED`。
- 重复签收：同一 `eventId` 再次消费返回 `SKIPPED`；不同 `eventId` 携带全部已登记案件号返回 `REUSED`；携带部分新案件号只补插缺失关系。
- 完成后重复签收：`COMPLETED` 申请收到新案件号时只追加案件关联，状态与完成时间不变。
- 完成后的重复提交：租户携带或不携带平台申请编号提交同一外部申请，均返回 `REUSED`，不修改人员、材料、问题件与状态。
- 补偿：`WAIT_AUDIT` 滞留且审核系统已签收时，补偿任务完成申请并补齐案件关联；审核系统未找到时重新交付并保持 `WAIT_AUDIT`。

## 异常场景与边界条件

- 审核签收消息租户与申请租户不一致：拒绝，不写消费登记、案件关联、轨迹或状态；消息重投耗尽后进入死信。
- 审核签收申请不存在：沿用 `CLAIM_APPLICATION_NOT_FOUND`，消息重投耗尽后进入死信。
- 审核签收申请处于 `PENDING_ACCEPT`、`ACCEPT_FAILED`、`ACCEPTED`、`UNDERWRITING` 或 `ISSUE`：拒绝，不产生部分写入；`ISSUE` 场景需在问题件关闭后重放消息。
- 审核签收申请存在未关闭问题件但状态为 `WAIT_AUDIT`（数据漂移）：按状态不合法拒绝，不完成申请。
- 审核签收并发：两个不同 `eventId` 同时到达，最多一方完成状态迁移；另一方重试后按 `COMPLETED` 追加案件关联。案件关联唯一约束保证不重复。
- 审核签收版本冲突：事务整体回滚，消息重试；重试后按当前状态重新判定。
- 审核签收完成事务中任一写入失败：消费登记、案件关联、状态、完成时间与轨迹全部回滚，不留下部分完成数据。
- `WAIT_AUDIT` 补偿查询失败：只记录错误日志，申请保持 `WAIT_AUDIT`，下一轮继续补偿。
- `WAIT_AUDIT` 补偿返回未找到并重新交付：不得改变状态；重复交付由审核系统按 `claimApplicationNo` 幂等处理。
- `COMPLETED` 申请下发问题件：返回状态不合法，不改变任何数据。
- `COMPLETED` 申请关闭已关闭问题件：按幂等返回 `closed=false`。
- 问题件下发人缺失：请求非法，拒绝落库；关闭人缺失：请求非法，拒绝关闭。
- 历史问题件关闭人为空：查询正常返回 `closedBy=null`，不影响下发人展示。
- 完成时间缺失：`COMPLETED` 申请必须拒绝保存或按数据异常处理，不允许出现无完成时间的终态。
- 详情查询 `COMPLETED` 申请：正常返回摘要、材料、问题件与案件关联；空集合返回 200 与空数组。
- 按案件号查询问题件：`COMPLETED` 申请返回 `hasOpenIssue=false`；案件关系不存在继续返回 404。

## 验收标准

1. `ClaimApplicationStatus` 包含 `COMPLETED`，状态机只允许本 Spec 列出的迁移；对 `COMPLETED` 的重新申请、补材、下发问题件均被拒绝或按重复请求复用。
2. 审核签收在 `WAIT_AUDIT` 时一个事务内完成：消费登记、缺失案件关联追加、状态迁移 `COMPLETED`、完成时间写入、`AUDIT_SIGNED` 轨迹写入；任一失败全部回滚。
3. 审核签收消息租户与申请租户不一致时拒绝，数据库无新增或变更；申请不存在时按既有错误码重投并进入死信。
4. 同一 `eventId` 重复消费返回 `SKIPPED`；同一申请不同 `eventId` 只补插缺失案件号；`COMPLETED` 后新增案件号只追加关系，状态与完成时间不变。
5. 审核签收申请处于 `ISSUE` 或其他非 `WAIT_AUDIT`/`COMPLETED` 状态时拒绝，不写入任何数据。
6. 问题件关闭不再覆盖下发人；下发、关闭、租户补材三种关闭来源的 `raisedBy` 与 `closedBy` 符合本 Spec 规则。
7. `COMPLETED` 申请重复提交返回 `REUSED`，签收可复用快照命中后不读聚合；携带平台申请编号的 `COMPLETED` 提交也不得触发重新申请或补材。
8. `WAIT_AUDIT` 滞留补偿在审核系统返回已签收时推进 `COMPLETED`，返回处理中时保持状态，返回未找到时重新交付且保持状态，查询失败时等待下一轮。
9. 详情查询摘要返回 `completedAt`，问题件视图返回 `raisedBy` 与 `closedBy`；空值返回 `null`；跨租户查询仍返回 404。
10. 数据库迁移后 `t_claim_application.completed_at`、`t_claim_application_issue.raised_by/closed_by` 与案件号查询索引存在；历史数据可正常读取。
11. 全量 Maven 构建、既有测试与新增测试通过，ArchUnit 分层与聚合封装规则通过。
12. 在运行栈上完成有保单、无保单、问题件、补材与审核完成五类黄金路径，重复消息与补偿场景结果符合本 Spec。

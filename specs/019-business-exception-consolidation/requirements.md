# 019 业务异常收敛

## 背景与目标

理赔申请服务当前有三套并行的业务异常：`ClaimApplicationIntakeException`、`ClaimApplicationIssueException`、`ClaimApplicationAsyncException`，各自配套错误码枚举、异常处理器与响应渲染。新增一个错误码时，需要同步修改异常类、枚举、处理器中的穷举 `switch` 与渲染器；018 增加 `AUDIT_SIGNED_INVALID` 时即因漏改 `switch` 导致编译失败。

本次目标是让异常只承担一件事：把可预期的业务拒绝从用例层带到入站层。业务错误码继续按业务域表达，HTTP 状态码在入站层集中映射。

## 业务规则

1. 可预期的业务拒绝统一抛出 `BusinessException`，携带 `BusinessErrorCode` 与面向调用方的错误说明，不携带 HTTP 类型。
2. 业务错误码按域保留枚举：申请接入、问题件、回调与异步链路；枚举统一实现 `BusinessErrorCode`，错误码字符串等于枚举常量名。
3. 错误码到 HTTP 状态码的映射只存在于入站适配层一张注册表，每个错误码必须有且只有一个映射。
4. 业务拒绝的 HTTP 状态码与错误码保持不变，与既有集成契约完全一致。
5. 请求体字段校验失败、报文无法解析由同一个全局异常处理器处理，返回 400，错误码取当前接口声明的“请求非法”码。
6. 未预期异常由同一个全局异常处理器兜底，返回 500，错误码取当前接口声明的“系统错误”码。
7. 每个 HTTP 入口控制器必须声明本接口的“请求非法”码与“系统错误”码，未声明视为接口契约缺失。
8. `ClaimApplicationExistenceMismatchException` 不属于业务异常：它是“事务内读不到、需要重建编号重试”的局部控制流信号。改为事务服务返回空结果表达，删除该异常类型。
9. 异常日志保持现有层级：业务拒绝记 WARN，未预期异常记 ERROR；日志包含 `traceId`、错误码与消息，不输出请求报文和敏感字段。
10. 响应结构仍为 `ApiResponse`，`success`、`code`、`message`、`traceId`、`data` 字段不变。

## 正常场景

- 业务用例抛出 `BusinessException`，入站层按错误码映射状态码并返回统一失败响应。
- 问题件字段校验失败，返回 400 与 `ISSUE_INTAKE_INVALID`，消息为第一个字段的校验提示。
- 承保回调报文无法解析，返回 400 与 `CALLBACK_INVALID`。
- 签收场景出现存在性判断与库中记录不一致，事务服务返回空结果，用例重新生成编号并重试，不抛异常。
- 未预期异常返回 500 与当前入口声明的系统错误码。

## 异常场景与边界条件

- 错误码缺少 HTTP 状态映射：查询注册表时立即失败，并在启动后的测试中暴露，不允许静默降级为 500。
- 控制器未实现接口错误码声明：ArchUnit 规则失败，禁止合入。
- 全局异常处理器拿不到当前控制器：视为框架级异常，按 500 兜底并记录 ERROR，不返回业务错误码。

## 本次范围

- `claim-application-service` 的异常类型、错误码枚举、异常处理器与失败响应渲染。
- 申请签收用例内部重试信号的返回值改造。
- 相关单元测试、ArchUnit 规则与架构文档。
- 运行栈错误响应回归。

## 非本次范围

- 不修改任何对外 HTTP 状态码、错误码、消息语义与响应结构。
- 不修改 MQ 死信策略、重投次数与消费者行为。
- 不修改网关、租户、案件、AI 模块。
- 不新增全局错误码；不为框架级异常引入平台通用错误码。
- 不调整领域模型、数据库、Redis 与 Outbox。

## 验收标准

1. 全仓仅保留一个对外业务异常类型 `BusinessException`，旧三个异常类删除且无引用。
2. 全仓仅保留一个 `@RestControllerAdvice`，旧三个异常处理器删除。
3. 签收、承保回调、问题件下发/关闭/查询的错误码与 HTTP 状态与 018 交付结果逐项一致。
4. 缺少必填字段与报文不可解析均返回 400 与对应入口的请求非法码。
5. 错误码映射完整性测试覆盖三个枚举的全部常量。
6. ArchUnit 规则校验所有控制器实现接口错误码声明，四条分层规则继续通过。
7. 全量 Maven 构建与测试通过；运行栈回归通过。
